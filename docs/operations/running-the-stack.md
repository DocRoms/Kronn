# Running the stack

Docker/WSL2 prerequisites and the `./kronn` lifecycle commands.

Moved out of `docs/AGENTS.md` (KT-191): needed when you actually run the
stack, not to start a task. Content verbatim.


- **Docker + Docker Compose** required for running the full stack.
- **Windows**: WSL2 is mandatory — Kronn mounts host binaries, Unix sockets, and Linux paths. Docker Desktop is not required; Docker Engine inside WSL works. Install WSL: `wsl --install`.
- Start: `./kronn start` or `make start` (builds and runs all services).
- Start natively (no Docker): `./kronn start-dev` — one command, runs backend + Vite with hot-reload against the **host** CLIs (the macOS path, since Docker can't run Darwin binaries / read the Keychain). UI on **:5173** (the backend serves API-only on :3140 in native mode). Equivalent to `make dev-backend` + `make dev-frontend` in two terminals.
- Stop: `./kronn stop` or `make stop`.
- Restart: `./kronn restart`.
- Logs: `./kronn logs` or `make logs`.
- Dev backend only: `make dev-backend` (watchexec with auto-reload).
- Dev frontend only: `make dev-frontend` (Vite dev server on :5173).
- After changing Rust models with `#[derive(TS)]`: run `make typegen` to regenerate `frontend/src/types/generated.ts`.
- After `docker compose build`, always restart the gateway: `docker compose restart gateway` or `docker compose down && docker compose up -d`.
- **macOS Kiro login is opt-in (silent by default)**: `maybe_login_kiro` (`kronn`) says **nothing** about Kiro unless `KRONN_KIRO_LOGIN=1`, which makes it probe + run `make kiro-login`. Decision logic is the pure `kiro_startup_action(os, authenticated, available, opt_in)` in `lib/agents.sh` (tested in `tests/bats/agents.bats`). Non-macOS / no-opt-in both return `skip`. Kiro is no longer auto-installed at boot (see next bullet), so by default there's nothing to log into until the user installs it.
- **macOS: only mirror agents the user actually installed; never pick a host-mounted Darwin binary.** The container `PATH` includes the host's `~/.local/bin` (`/host-bin/local`), so `which` can resolve a macOS (Mach-O) `claude`/`codex`/… that can't exec in the Linux container (symptom: a version reading "Exec format error"). Invariants:
  1. `find_binary` (`backend/src/agents/mod.rs`) consults `should_skip_darwin_host_binary()` on **both** the `which` path and the dir-scan, so a Darwin binary is skipped in favour of the Linux copy / `npx` runtime.
  2. `entrypoint.sh` mirrors a Linux copy **only** when `host_darwin_needs_linux_copy()` is true — i.e. the agent resolves exclusively under `/host-bin/*` (the user has it on their Mac). It does **not** install agents that are absent everywhere; the UI offers an explicit Install for those. This is why a Claude-only Mac shows Claude installed and everything else (incl. Kiro) as "Install".
  3. **`runtime_available` (npx) ≠ installed in the UI.** Both the Setup Wizard (`SetupWizard.tsx`) and Settings → Agents (`AgentsSection.tsx`) show the enable/disable toggle only for `installed` agents; npx-only agents get the Install button + a `runtime OK — via npx` hint, never "Activé".
  When adding an npm agent, extend `MACOS_HOST_BIN_SKIP`, `entrypoint.sh`, and the npx case in `probe_runtime` — the `cross_agent_macos_skip_covers_npm_agents` test enforces the first.
- **Auth bypass can't see the real client IP behind Docker Desktop (macOS/Windows).** `auth_middleware` (`backend/src/lib.rs`) skips auth for localhost via `is_local_ip(X-Real-IP)`, but Docker Desktop NATs every published-port request to the Docker network gateway (e.g. `192.168.97.1`). `is_local_ip` intentionally rejects `192.168/16` + `10/8` (the `tailscale_lan_and_public_are_not_local` test pins this — broadening it lets LAN peers skip auth). If auth is on, the browser gets `401` → "Cannot connect to backend". Two layers handle this: (1) `core::config::load` seeds `auth_enabled = core::env::auth_on_by_default()` (= `!is_docker()`) when it generates the token, so a **fresh config under Docker defaults to auth OFF** (token still created for opt-in multi-user) → no first-launch 401; native keeps auth on. (2) `auth_middleware` honours the `auth_enabled` master switch — it skips auth entirely when false, even with a token present, so the switch is the escape hatch and is sticky (`config.rs` only re-generates a token when absent). An exposed multi-user Docker server must set `auth_enabled = true` explicitly. Do NOT "fix" the bypass by widening `is_local_ip` to private ranges (the `tailscale_lan_and_public_are_not_local` test pins that).
- **RTK detection is host-aware too.** `rtk` is baked into the container image, but Kronn is a bridge — RTK must live on the **host** (where CLIs run) for `rtk gain` and the agent hooks to actually work. `core::rtk_detect::rtk_binary_available()` therefore checks `KRONN_HOST_BIN` under Docker (NOT the container's `/usr/local/bin/rtk`); native uses `which`. When RTK isn't on the host, the Settings RTK card shows its Install (curl) flow instead of "Activate". Same principle as agent detection.
- **npm `-g` installs go to `~/.local`, not `/usr/local`.** The container runs as non-root `kronn`, so the default root-owned global prefix fails with `EACCES`. `backend/Dockerfile` sets `ENV NPM_CONFIG_PREFIX=/home/kronn/.local` (already first on `PATH`); every `npm install -g <agent>` (the Install button via `install_agent`, the boot mirror in `entrypoint.sh`) lands in `/home/kronn/.local/bin`. Don't reintroduce a bare-`/usr/local` `npm install -g` or a per-call `--prefix` — the image-level env is the single source of truth. Note: `~/.local` is not volume-backed, so button-installed agents don't survive a container rebuild (Claude is re-mirrored at boot from the host install; others need re-install or a persistent volume).
- **The agent "Install" button is host-aware.** A Docker container can't install onto the host (read-only bin mount, no host-exec), so under Docker the Install button is **disabled** with a note pointing to the host-side `kronn` CLI. The frontend learns the deployment from **`/api/health`'s `in_docker`** (raw JSON → `core::env::is_docker()` → `KRONN_DATA_DIR`, Docker-only). It's threaded as the `inDocker` prop to `SetupWizard` + `AgentsSection` (default `false`). Desktop-only commands use the allowlisted `window.__TAURI__.core.invoke` bridge enabled by `withGlobalTauri`; this is runtime detection, never Docker detection. Platform intent: Tauri → install on host (native); Docker Linux/WSL → host install = Linux binary Kronn runs via the mount; Docker macOS → host Darwin binaries can't run in the Linux container, so the macOS path is the Tauri app.
