# Agent fallback, per mode (KT-1518, redesigned by KT-1693)

When an agent's provider cannot serve a turn — a rate limit, a quota or credits spent, an outage that survived its retries, a CLI that is not signed in — the turn continues on another configured agent instead of stopping. The policy is one module, applied by three surfaces.

## Configuration

**One fallback per agent and per mode.** An agent has up to six modes: `eco`, `standard`, `advanced` (the three text modes, i.e. the economy / default / reasoning tiers), `decision`, `image` and `video`. Settings > Agents shows, on each agent card, one row per mode the agent has — « [current model] → [fallback] → [inherited fallback, dashed] » — and every pill carries its transport badge: **CLI**, **HTTP** or **Local**. There is no « paid » badge and no opt-in: everything but a local model costs something, so enabling a fallback is the consent. A fallback is off by default. « + Add a fallback » opens a menu filtered by kind of mode, grouped by agent, each model shown with its mode and its transport; an agent already in the chain is disabled. A search field at the top filters by agent and model name; the arrows, Enter and Escape drive the menu from the keyboard. The menu is drawn in the page body and placed from its anchor (`placeMenu`: flipped onto the anchor's right edge or above it when needed), so the card never clips it. Clicking a pill changes it, ✕ removes it. [src: file: frontend/src/components/settings/FallbackRow.tsx:298] [src: file: frontend/src/lib/fallbackChain.ts:150]

The fallbacks are stored on the agent's section of `config.toml` as `[[agents.claude_code.mode_fallbacks]]` (`row`, and the `fallback` with its `agent`, optional `model` and optional `mode`) and served by `GET`/`POST /api/config/agent-fallback` (the POST sets or, with `fallback: null`, removes one mode row). [src: file: backend/src/models/setup.rs:993] [src: file: backend/src/api/setup.rs:6878]

**One « Models and fallbacks » block per card (KT-1706).** On every card of Settings > Agents — CLI agents, Ollama, the HTTP connections (LiteLLM, NVIDIA, OpenRouter, custom) and ComfyUI — the rows sit in one block right under the card header, ahead of the secondary settings (concurrency, « Can act in Kronn », downloads, Restricted): `Mode · [model ▾] → [fallback pill] ✕  + Add a fallback`. The model picker of a row sets that mode's model (the tier model, or the connection's / ComfyUI's slot for the mode) and replaces the former per-tier block, Ollama's « Model per tier » and the fallback rows at the bottom of the card; it shows the resolved model, never « default model » when one is configured. A change is saved at once and the row is left as it was when the backend refuses. The agents' rows (CLI, Ollama) are the `mode_fallbacks` above. [src: file: frontend/src/components/settings/AgentsSection.tsx:719]

**Connections and ComfyUI.** A named HTTP connection is not an `AgentType`, so its rows live apart, in `[[agents.connection_fallbacks]]` (`owner` = the connection id or `local:comfyui`, `row`, and the `fallback` = `connection` + optional `model`), served by `POST /api/config/connection-fallback` and returned in the `media` list of the same overview. A connection has a row per mode it serves (eco / standard / advanced / decision / image / video as configured); ComfyUI has `image` and `video` only. Kind rules are the same: text to text, `decision` to `decision`, `image` to `image`, `video` to `video`, never to the source itself; a loop or a chain past `MAX_CHAIN_DEPTH` is refused with the reason. [src: file: backend/src/models/setup.rs:1171] [src: file: backend/src/api/setup.rs:6882] [src: file: backend/src/core/connection_fallback.rs:117] The menu lists the other connections' configured models (and ComfyUI's current image / video model). [src: file: frontend/src/lib/mediaFallbackOptions.ts:30] [src: file: frontend/src/components/settings/ConnectionFallbackRow.tsx:35]

**Layout of the block (KT-1706 review).** The block carries the card's own content inset: a CLI card's block is a direct child of the card, an HTTP connection card's block a direct child of its `.set-ext-api-conn`, and Ollama's and ComfyUI's sit inside their `.set-ollama-card` padding. What the catalogue says about the pickers (loading, load failure, nothing known, stale) is one muted line under the block's title (`CatalogHint`), in plain words per reason (`modelCatalog.staleHint.*`), never the raw reason code. The model picker grows into the room the fallback pill leaves and keeps its full label in the field's `title`. Where the HTTP connection cards are: Settings > Agents, « External API » zone (third of the three mode zones, after Local). Each named connection is a `[data-testid="ext-api-connection"]` card (`data-connection-id`, `data-preset` = `lite_llm` / `nvidia` / `open_router` / custom) whose block is `[data-testid="connection-models-<connection id>"]`, with rows `connection-fallback-<connection id>-<mode>` and pickers `connection-model-<connection id>-<mode>`. A connection shows there only once it has been created; with none configured the zone shows its empty state and no block. ComfyUI's block is `[data-testid="agent-fallback-comfyui"]` (rows `connection-fallback-local:comfyui-image` and `-video`), in the Local zone.

**What the runner does with them.** A media generation the provider refuses before accepting it (no provider handle, no source image) is retargeted to the next usable link of its row, then to the rows of the fallbacks, never a source it already left; a generation the provider may already be producing is never moved. [src: file: backend/src/agents/media_runner.rs:747] A text or decision request a named connection cannot serve — a discussion turn or a workflow Agent step — continues on the next usable connection of its mode row (`next_text_target`: a link needs a configured model for the mode and a runnable endpoint). [src: file: backend/src/core/connection_fallback.rs:289]

**Every installed agent takes part**, OpenCode included: an agent needs no concurrency slot to have rows or to be offered as a target. [src: file: backend/src/core/agent_fallback.rs:344]

**Kind rules.** Text modes fall back to any agent/model of a text mode (eco, standard or advanced); `image` to `image`; `video` to `video`; `decision` to `decision`. An incompatible target is never offered by the menu and is refused by the backend with the reason. A fallback's `mode` is the mode of the model it runs on; without it, the mode of the row it replaces. [src: file: backend/src/core/agent_fallback.rs:462]

**Chaining.** When the fallback is itself unavailable, the fallback set on ITS own mode row applies (the row of the target agent, in the mode the target runs in), at most `MAX_CHAIN_DEPTH` (4) links, an agent never twice and never itself. A row that would make a loop or a chain past the limit is refused when saved; a loop written by hand in `config.toml` is simply not walked. The inherited links are shown dashed, with « set on <agent>'s card »; clicking one opens that card. [src: file: backend/src/core/agent_fallback.rs:389] [src: file: backend/src/core/agent_fallback.rs:534]

**Access.** A fallback never gets more access (`full_access`) than the agent it replaces; this is refused when saved and re-checked when a link is chosen.

**Migration.** The agent-level chain of 0.15.3 (`fallback_chain`) is carried at start-up onto the text rows of that agent: its first link on eco, standard and advanced, the next links on the rows of the link before them, so « A → B → C » is still « A → B → C ». Where a row is already set (an agent's own chain wins), the extra link is dropped; the legacy field is emptied and never written again. A discussion's stored override (one list for the whole discussion) becomes the same override on each text mode, an empty one cutting them. `allow_paid` is read and ignored. [src: file: backend/src/core/agent_fallback.rs:597] [src: file: backend/src/core/config.rs:618]

**Overrides, per mode.** With no override, the row of the agent a turn starts on, for the mode the turn runs in, applies. A discussion (discussion settings, one row per text mode, right under the discussion's agent) and a workflow Agent step (step editor, the row of the step's tier, right under the step's agent and mode picker — visible without opening the step's « advanced » section) can instead use their own fallback, go back to the default, or cut the fallback — the same component as the cards. A discussion's overrides are stored per mode in `discussion_fallback_overrides` and served by `GET`/`PUT /api/discussions/{id}/fallback` (the PUT carries the `mode`); a step's is `agent_settings.fallback` (`None` = default, `Some([])` = cut). An override replaces the first link; the rows of its fallbacks then go on. [src: file: backend/src/api/discussions/agent_fallback_override.rs:67] [src: file: backend/src/models/workflows.rs:1908]

Without a `model`, a link runs the SAME tier as the interrupted turn (economy stays economy), resolved on its own agent: a model name belongs to one provider, so the failing agent's model is never carried over. The menu therefore offers a model-less choice on the row's own mode only.

## What triggers it, and what never does

Unchanged from KT-1518. `classify_trigger` answers `rate_limit`, `quota_exhausted`, `outage` or `not_authenticated` from the provider's own words, and `None` for everything else: a task failure, a refusal, a failing test, and the stall or timeout of the work itself — even when its last output quotes a 429. [src: file: backend/src/core/agent_fallback.rs:110] An outage is retried on the same agent first; only then does the fallback take over.

## The three surfaces

| Surface | Where | What happens |
|---|---|---|
| Discussion turn | `intercept_failed_turn` [src: file: backend/src/api/discussions/agent_fallback.rs:275] | The same dispatch is re-queued on the fallback and pinned to it (`dispatch_fallback_pins`: origin agent, target agent, model, tier, hops); the refused reply is replaced by one System line. |
| Workflow Agent step | `continue_after` [src: file: backend/src/workflows/agent_fallback_step.rs:179] | The step is rerun on a copy carrying the fallback agent (tier, budget and prompt kept); the line leads the step's output, and the step's provenance names the agent that really answered. |
| Task worker | `worker_after_quota` [src: file: backend/src/api/discussions/agent_fallback.rs:340] | The execution is reassigned to the fallback in its own room and worktree, through the KT-1564 reassignment; the agent it started on is kept in `execution_fallback_origins`, its rows being the ones walked; the parent room gets the line. A campaign's own `quota_fallback` opt-in is asked first for a quota refusal. The rules specific to a task worker are in « Task workers » below. |

The text modes are the ones a turn, a step and a worker run in. The decision, image and video rows are stored, validated, chained and shown like the others; the runtime hook of those step types is not part of this change.

The line: « Codex · gpt-5.6-sol: quota exhausted until 14:00 UTC → continued with Claude Code · sonnet [CLI] » — from which agent/model, why, until when, to which agent/model and over which transport (the model is the link's own, else the mode it keeps: `eco mode`). The discussion shows it as a System line on the turn, the run view on the step (it leads the step's output); both render it as `from → to [transport] · reason · until`. A line written by 0.15.3 (`->`, no transport) is still read. When a fallback is configured and nothing in it can take over: « Codex: quota exhausted → no fallback (<why>) ». ## Task workers (KT-1713)

A task worker commits, merges the target into its branch and delivers from a **linked worktree**, whose git directory lives under the main repository's `.git/worktrees/<name>`, outside the writable roots of a Codex sandbox: every git write there fails (`ORIG_HEAD.lock: Operation not permitted`), so a Codex worker ends « without delivery ». Three rules follow.

- **Codex is never a task-worker fallback.** The selection asks a worker for `task_worker` on top of `write_access`, and `capability_gap` refuses Codex for it with « Codex task-worker fallback is disabled: its sandbox cannot write the linked worktree Git administrative directories… ». The next link of the chain is tried; when nothing else can take over, the stop line is posted in the parent room. Codex stays a valid *declared* worker and a valid fallback for a room turn or a workflow step, which do not write through a linked worktree. [src: file: backend/src/core/agent_fallback.rs:221] [src: file: backend/src/core/agent_fallback.rs:188]
- **The fallback is temporary.** The reassignment records the worker it leaves (`task_execution_quota_origin`) with the instant the window ends: the reset the provider announced, else the re-try window of the cooldown (`plan.until`), so a refusal that announced nothing still has a return. The KT-1564 sweep brings a `Working` or quota-parked execution back; a **resume** of an `Interrupted` execution (the fallback worker ended without delivery, a restart…) now does the same before waking anyone: once the window has ended it reassigns to the declared worker — same child room, worktree and tier — instead of redispatching the alternative. While the window is open the resume wakes the current worker as before; a return the reassignment refuses (the declared provider is still refused elsewhere) falls back to that ordinary wake. [src: file: backend/src/api/discussions/agent_fallback.rs:577] [src: file: backend/src/api/orchestration.rs:1720] [src: file: backend/src/db/orchestration.rs:3421]
- **The room says which execution.** Every line about a task worker starts with « Task worker execution <id>: »: the fallback notice, the stop line, and the return line « … the quota window that moved it to <agent> has ended → back on its declared worker <agent> », posted in the parent room (`agent-fallback-return:<execution>:<dispatch>`) and carried in the handoff of the worker's own room. [src: file: backend/src/api/orchestration.rs:1703]

## Cooldown and return

The failing agent is left alone until the reset the provider announced (`Retry-After`, `resets 4pm (Europe/Paris)`…), else a short re-try window by trigger (5 minutes for a rate limit or an outage, the KT-1657 re-check interval for a quota, 30 minutes for a missing login). It is a re-try window, not a guess of the provider's schedule: after it the next turn tries the agent again, and a new refusal renews it. The cooldown is per agent, whatever the mode. [src: file: backend/src/core/agent_fallback.rs:931]

While it lasts, a NEW room turn or workflow Agent step starts straight on the fallback. [src: file: backend/src/api/discussions/agent_fallback_start.rs:20] [src: file: backend/src/core/agent_fallback.rs:1032] An expired cooldown is simply not read: the agent is back with nothing to undo. A provider that answers the KT-1657 re-check, a forced readiness check, or a new/changed API key ends the cooldown at once. Settings > Agents shows it on the card.

## The quota-back decision points

When the KT-1657 re-check finds the provider still refusing, the fallback is the alternative to waiting: a quota-paused workflow run has its refused step switched to the next usable link (the same gesture as the owner's « switch agent »), and a task execution escalated on an unannounced quota (KT-1664) is reassigned to it. When the provider answers instead, `resume_quota_escalation_after_probe` resumes the original worker as before. [src: file: backend/src/workflows/agent_fallback_step.rs:274] The run's « switch agent » control offers the configured fallback first (the standard row of the agent) and preselects it.

## A fallback mid-turn is never cancelled; a waiting one is announced (KT-1758)

The return to the declared worker (`return_quota_escalations_past_reset`) cancels the dispatch of the worker it replaces. When that worker is a fallback that is **mid-turn** — its dispatch is `Running` and `agent_started_at` is set — the return would throw the turn's work away unsaved, so it waits: `fallback_executions_past_origin_reset` does not list such an execution and `ensure_quota_return_still_due` refuses it inside the reassignment transaction (`execution_turn_in_progress`, one SQL predicate for both). The watchdog asks again every 15 s, so the return happens right after the turn ends (a delivery under review is left alone, as before). A fallback that has **not started** (queued, or claimed with no agent yet) loses nothing and is replaced as before.

A fallback whose dispatch stays `Pending` is no longer silent. After 5 minutes (`FALLBACK_DISPATCH_WAIT_NOTICE_AFTER_SECONDS`) the watchdog posts one line in the parent room (`fallback-dispatch-waiting:<dispatch>`) naming the cause the queue holds against it, most specific first: the runtime that could not start (`runtime_unavailable:` — the 30 s retry that never spends an attempt), an audit writing `docs/`, the `__task_workers` cap, the provider's own per-agent cap (default 1 for every local agent, OpenCode included), a retry delay, older workers ahead in launch order — or « no cause recorded », which is itself the finding. The claim path itself is covered by `every_fallback_dispatch_of_a_refused_run_gets_its_turn_in_launch_order` (seven refused workers, one slot, launch order, none left `Pending`).

### What holds a fallback dispatch, and what does not (KT-1758)

A fallback's dispatch is a new row created `Pending` with `available_at` = now. It is **not** dated by the provider it left: no writer reads `task_execution_quota_origin.reset_at`, `provider_quota_generations.reset_at` or the rearm schedule to date a dispatch, and the hold on the original provider is tested only against dispatches whose agent is that provider. The reassignment still calls `make_available_now` on the replacement, so a replay of the same handoff over a row dated ahead is brought forward (only `Pending`, `attempts = 0`, so a backoff earned by a real attempt stays). [src: file: backend/src/db/agent_dispatch.rs:1465] [src: file: backend/src/api/orchestration.rs:15086]

Every writer of `available_at` on a row that can be `Pending`, so that a value seen in the table can be traced:

| Writer | Value | Leaves |
|---|---|---|
| `enqueue_with_connection` | now | `attempts` 0, no claim |
| `recover_after_restart` | restart time | `backend_restarted` |
| `apply_watchdog_stall` | now + 2 s | `watchdog_stall_redispatch` |
| `retry_after` | now + delay (5 s silent crash, 15–30 s overload, 30 s outage, 0 for a fallback) | the reason |
| `defer_runtime_unavailable` | now + 30 s (5 s for the audit hold); `attempts` − 1, `claimed_at` and `agent_started_at` cleared | `runtime_unavailable: …` / `audit_running: …` |
| `release_unstarted_claim` | now; `attempts` − 1, `claimed_at` cleared | `claim_handoff_dropped` |
| `advance_chain_trigger` | now | none |

[src: file: backend/src/db/agent_dispatch.rs:1082] [src: file: backend/src/db/agent_dispatch.rs:1352] [src: file: backend/src/db/agent_dispatch.rs:1400] [src: file: backend/src/db/agent_dispatch.rs:1417] [src: file: backend/src/db/agent_dispatch.rs:1441] [src: file: backend/src/db/agent_dispatch.rs:1623] None of them is derived from a quota reset, and none lasts more than 30 s. So an `available_at` minutes away from `created_at`, on a row with `attempts` 0 and no `claimed_at`, is the **last** `defer_runtime_unavailable` / `release_unstarted_claim` of a claim that did not reach the agent (it decrements `attempts` and clears the claim), not a dated start: it equals the time of that last bounce (+ 30 s for a deferral). That is how a `+2 min` / `+11 min` after the original provider's reset reads, and it points at a start that kept failing, not at a hold — an inference from the writers above, not a measurement: the live rows were not readable from the worker's sandbox. `last_error` on such a row (`runtime_unavailable: <reason>`) names it, which is why a cancellation no longer erases it.

`cancel_for_discussion` and `cancel_for_discussion_by_id` keep the previous `last_error`: `cancelled (was: runtime_unavailable: …)`, or plain `cancelled` when there was none. [src: file: backend/src/db/agent_dispatch.rs:1479] The workflow cancellations keep writing their own reason.
