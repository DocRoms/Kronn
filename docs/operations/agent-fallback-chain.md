# Agent fallback, per mode (KT-1518, redesigned by KT-1693)

When an agent's provider cannot serve a turn — a rate limit, a quota or credits spent, an outage that survived its retries, a CLI that is not signed in — the turn continues on another configured agent instead of stopping. The policy is one module, applied by three surfaces.

## What triggers it, and what never does

Unchanged from KT-1518. `classify_trigger` answers `rate_limit`, `quota_exhausted`, `outage` or `not_authenticated` from the provider's own words, and `None` for everything else: a task failure, a refusal, a failing test, and the stall or timeout of the work itself — even when its last output quotes a 429. [src: file: backend/src/core/agent_fallback.rs:110] An outage is retried on the same agent first; only then does the fallback take over.

## Task workers (KT-1713)

A task worker commits, merges the target into its branch and delivers from a **linked worktree**, whose git directory lives under the main repository's `.git/worktrees/<name>`, outside the writable roots of a Codex sandbox: every git write there fails (`ORIG_HEAD.lock: Operation not permitted`), so a Codex worker ends « without delivery ». Four rules follow.

- **A generic worker never moves to an HTTP model (KT-1991).** A worker with no prelocalised scope (`worker_scope`) builds, runs the tests and commits: `plan` asks it for `shell` on top of `write_access` and `task_worker`, on every worker path (a failed turn, a quota refusal after the campaign's opt-in, a launch refusal, the quota-back decision point). `capabilities` gives an HTTP agent (Ollama, LiteLLM, NVIDIA) workspace writes but no shell, and `capability_gap` names it « it has no shell to build, run the tests or commit ». The walk goes on to a CLI link. A prelocalised worker asks for no shell and still continues on an HTTP link. `quota_fallback_agents` only governs quota refusals; a rate limit, an outage or an authentication failure follows this chain at once. [src: file: backend/src/core/agent_fallback.rs:217] [src: file: backend/src/core/agent_fallback.rs:254] [src: file: backend/src/api/discussions/agent_fallback.rs:183]
  - **The campaign's quota step reads the same rule (KT-2000).** Before the chain, a quota refusal looks at the launch's `quota_fallback_agents`, else the campaign's `allowed_agents`. For a generic worker, `provider_fallback_among` skips every candidate whose `capabilities(..).shell` is false, the capability the chain reads, so an HTTP model is never taken there either, named or merely allowed; a mixed list gives its CLI agent, a prelocalised worker keeps its HTTP candidates. The skip says nothing of its own: with no candidate left the flow goes on as when none exists. [src: file: backend/src/api/discussions/runtime.rs:932#needs_shell]
  - **The reassignment refuses it too (KT-2000).** Every move Kronn makes ends in `reassign_native_execution_for_dispatch`: with `ReassignCause::QuotaFallback`, an execution with no `worker_scope` and a target whose `capabilities(..).shell` is false, it bails before anything is written, with a message carrying `NO_SHELL`. Both callers already handle a refused move: the chain posts its stop line in both rooms, the quota step goes on to the chain and then the escalation. `plan` reads an execution it cannot find as generic (`is_none_or`), so an unknown worker asks for a shell. The rule is about Kronn's own moves; an explicit choice, by a person or by the principal, stays possible: the launch boundary accepts a generic worker on an HTTP agent, and so does a reassignment with `ReassignCause::Human` (`task_exec_reassign`, the UI). The quota returns hand the execution back to the worker it declared. [src: file: backend/src/api/orchestration.rs:15779#QuotaFallback] [src: file: backend/src/api/discussions/agent_fallback.rs:186#is_none_or]
  - **When nothing is left, the worker is not moved; what follows depends on the path.**
    - *A failed turn* (rate limit, outage, authentication): `post_stop` writes the chain's stop line in both rooms, « Task worker execution <id>: Claude Code: rate limited → no fallback (No fallback could take over from Claude Code: LiteLLM cannot take this turn: it has no shell to build, run the tests or commit.) » in the parent, the same line without the prefix in the worker's room. The failure is then settled as without a chain: the dispatch fails and the execution is `Interrupted`. [src: file: backend/src/api/discussions/agent_fallback.rs:363]
    - *A quota refusal*: the chain's stop line as above (« quota exhausted → no fallback (…) »), then the execution is `Escalated` and the parent room reads « Intervention humaine requise — quota épuisé … Aucun provider alternatif explicitement autorisé n'est disponible … ». A `quota_fallback_agents` entry skipped for its missing shell is not named. [src: file: backend/src/api/discussions/runtime.rs:1577#escalate_execution_for_dispatch_quota]

- **Codex is never a task-worker fallback of the chain.** The selection asks a worker for `task_worker` on top of `write_access`, and `capability_gap` refuses Codex for it with « Codex task-worker fallback is disabled: its sandbox cannot write the linked worktree Git administrative directories… ». ## Cooldown and return

The failing agent is left alone until the reset the provider announced (`Retry-After`, `resets 4pm (Europe/Paris)`…), else a short re-try window by trigger (5 minutes for a rate limit or an outage, the KT-1657 re-check interval for a quota, 30 minutes for a missing login). It is a re-try window, not a guess of the provider's schedule: after it the next turn tries the agent again, and a new refusal renews it. The cooldown is per agent, whatever the mode. [src: file: backend/src/core/agent_fallback.rs:931]

While it lasts, a NEW room turn or workflow Agent step starts straight on the fallback. [src: file: backend/src/api/discussions/agent_fallback_start.rs:20] [src: file: backend/src/core/agent_fallback.rs:1032] An expired cooldown is simply not read: the agent is back with nothing to undo. A provider that answers the KT-1657 re-check, a forced readiness check, or a new/changed API key ends the cooldown at once. Settings > Agents shows it on the card.

## The quota-back decision points

When the KT-1657 re-check finds the provider still refusing, the fallback is the alternative to waiting: a quota-paused workflow run has its refused step switched to the next usable link (the same gesture as the owner's « switch agent »), and a task execution escalated on an unannounced quota (KT-1664) is reassigned to it. When the provider answers instead, `resume_quota_escalation_after_probe` resumes the original worker as before. [src: file: backend/src/workflows/agent_fallback_step.rs:274] The run's « switch agent » control offers the configured fallback first (the standard row of the agent) and preselects it.

## A fallback mid-turn is never cancelled; a waiting one is announced (KT-1758)

The return to the declared worker (`return_quota_escalations_past_reset`) cancels the dispatch of the worker it replaces. When that worker is a fallback that is **mid-turn** — its dispatch is `Running` and `agent_started_at` is set — the return would throw the turn's work away unsaved, so it waits: `fallback_executions_past_origin_reset` does not list such an execution and `ensure_quota_return_still_due` refuses it inside the reassignment transaction (`execution_turn_in_progress`, one SQL predicate for both). The watchdog asks again every 15 s, so the return happens right after the turn ends (a delivery under review is left alone, as before). A fallback that has **not started** (queued, or claimed with no agent yet) loses nothing and is replaced as before.

A fallback whose dispatch stays `Pending` is no longer silent. After 5 minutes (`FALLBACK_DISPATCH_WAIT_NOTICE_AFTER_SECONDS`) the watchdog posts one line in the parent room (`fallback-dispatch-waiting:<dispatch>`) naming the cause the queue holds against it, most specific first: the runtime that could not start (`runtime_unavailable:` — the 30 s retry that never spends an attempt), an audit writing `docs/`, the `__task_workers` cap, the provider's own per-agent cap (default 1 for every local agent, OpenCode included), a retry delay, older workers ahead in launch order — or « no cause recorded », which is itself the finding. The claim path itself is covered by `every_fallback_dispatch_of_a_refused_run_gets_its_turn_in_launch_order` (seven refused workers, one slot, launch order, none left `Pending`).

### What holds a fallback dispatch, and what does not (KT-1758)

A fallback's dispatch is a new row created `Pending` with `available_at` = now. It is **not** dated by the provider it left: no writer reads `task_execution_quota_origin.reset_at`, `provider_quota_generations.reset_at` or the rearm schedule to date a dispatch, and the hold on the original provider is tested only against dispatches whose agent is that provider. The reassignment still calls `make_available_now` on the replacement, so a replay of the same handoff over a row dated ahead is brought forward (only `Pending`, `attempts = 0`, so a backoff earned by a real attempt stays). [src: file: backend/src/db/agent_dispatch.rs:1502] [src: file: backend/src/api/orchestration.rs:15103]

### Root cause: a permanent refusal was deferred forever (KT-1758)

The fallback target (OpenCode, native ACP) is refused **as a task worker** at spawn: `task_worker_route_policy` returns `NATIVE_ACP_TASK_WORKER_REFUSAL`, and `start_agent_with_config` words it `Task worker refused: …`. `agent_start_failure_outcome` classed that string as `AgentExecutionOutcome::RuntimeUnavailable` (anything it did not know was permanent), and the runtime's handler called `defer_runtime_unavailable`: back to `Pending`, `available_at` + 30 s, `attempts` − 1, `claimed_at` and `agent_started_at` cleared — so the dispatch looked never claimed, and a refusal that waiting cannot change was retried every 30 s with no bound and no trace in the room, until the quota return cancelled it. [src: file: backend/src/agents/runner.rs:3951] [src: file: backend/src/api/discussions/streaming.rs:1295] KT-1749 stops the fallback from *selecting* such an agent; the engine is robust on its own regardless:

- **A refusal waiting cannot change is settled, not deferred.** `Task worker refused:` is `PreflightFailed` (the worker's room gets the error card as for any other settled refusal).
