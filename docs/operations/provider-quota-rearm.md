# Provider quota re-arm

Kronn blocks new delegations for a provider after a real quota-exhaustion recovery marker on an escalated execution. Escalations attached to Planning tasks in `done` or `archived` no longer count as active blockers. [src: file: backend/src/db/orchestration.rs:2614-2640#provider_has_open_quota_exhaustion]

A human confirmation in Config > Agents can acknowledge that one provider's quota is available again. The action records an idempotent provider-scoped audit event and watermark; it does not restart, cancel, or change any historical execution or recovery row. A later quota marker for that provider is newer than the watermark and blocks launches again. [src: file: backend/src/db/orchestration.rs:3108-3149#rearm_provider_quota]

The re-arm endpoint is a browser route and is not part of the task-worker MCP surface. [src: file: backend/src/lib.rs:3289-3292#rearm_provider_quota] [src: file: backend/src/api/orchestration.rs:15519-15551#rearm_provider_quota]

## Reassigning to the same provider is a re-arm (KT-838)

One exhausted quota often stops several executions at once, each escalation taking the next quota generation of that provider. Reassigning an `Escalated` execution to the very provider whose quota stopped it (its recovery marker is `quota_exhausted:<provider>`) is the human's "the quota is back" signal for the whole outage: the reassignment re-arms the provider in its own transaction, so every earlier generation stops blocking, whichever execution is reassigned first. The audit event has `actor_kind = human` and `actor_id = reassign:<execution id>`. Reassigning to a different provider says nothing about the first one and re-arms nothing. A new real quota failure takes a newer generation and blocks the provider again. [src: file: backend/src/api/orchestration.rs:13787-13802#quota_retry] [src: file: backend/src/db/orchestration.rs:2621-2654#is_quota_retry_on_same_provider] [src: file: backend/src/api/orchestration.rs:15519-15532#rearm_provider_quota] [src: file: backend/src/db/orchestration.rs:2574-2580#latest_generation]

## Announced reset time

When the provider's refusal names a reset time in a zone (Claude Code: `resets 4:20pm (Europe/Paris)`, or with a day: `resets Oct 3, 4pm (Europe/Paris)`), it is resolved to a UTC instant and stored on the provider's quota generation row (`provider_quota_generations.reset_at`). Settings > Agents shows it beside the re-arm button as "Rearmable at 16:20" in the browser's local time. Since KT-1564 it is also the refusal's expiry (next section). A refusal without a zone gets no instant, since the backend's own zone may not be the user's. A later refusal that names no time keeps a still-future announcement of the same outage and drops a passed one. [src: file: backend/src/api/discussions/orchestration.rs:1617-1681#announced_quota_reset] [src: file: backend/src/db/orchestration.rs:2527-2548#reset_at] [src: file: frontend/src/components/settings/AgentsSection.tsx:928-940#quotaResetTime]

## The announced reset closes the escalation (KT-1564)

A refusal that announced its reset expires on its own. Once `provider_quota_generations.reset_at` has passed, `provider_has_open_quota_exhaustion` stops counting the escalation, and the resilience watchdog (every 15 s) hands each execution still `Escalated` with `quota_exhausted:<provider>` back to that same provider, tier, model and profile through the same-provider reassignment of KT-838: the escalation closes (`Escalated -> Working`), the provider is re-armed with `actor_kind = backend` and the worker gets a new dispatch in its existing room. It never picks another provider, and never rebuilds the worker from the campaign's `default_worker` or `allowed_agents`. A refusal that announced no reset never expires: only a human re-arm or reassignment closes it. [src: file: backend/src/db/orchestration.rs:2741#executions_past_quota_reset] [src: file: backend/src/api/orchestration.rs:706#return_quota_escalations_past_reset]

The sweep skips the executions of a run whose `control_state` is not `running` (paused, awaiting a human, cancelled, completed, failed) or whose `status` is not `active`, and the reassignment re-checks that, and that the execution is still parked on the passed reset, inside its own transaction (`ensure_quota_return_still_due`). A person who moves the execution between the sweep's read and its write wins: the sweep is refused and cancels nothing. [src: file: backend/src/db/orchestration.rs:2983#ensure_quota_return_still_due]

## Provider fallback is its own opt-in (KT-1564)

`allowed_agents` only lists the providers a worker may be given. A switch to another provider when a dispatch is refused for quota needs the campaign's separate `quota_fallback` flag (`orchestration_runs.quota_fallback`, off by default, field `quota_fallback` of `POST /api/orchestration/campaigns`). Without it the execution escalates and waits for its own provider's reset, whatever `allowed_agents` or `default_worker` say. [src: file: backend/src/api/discussions/runtime.rs:766#try_quota_provider_fallback_among]

With the opt-in, the fallback keeps the execution's tier and profile (a model name is provider-specific and is dropped), records the worker it leaves and the reset the refusal announced in `task_execution_quota_origin`, and the same sweep hands the execution back to that exact worker once the reset has passed (only while it is `Working`, or parked on its own quota refusal). A fallback whose refusal announced no reset is never undone by Kronn. The origin is only deleted by a human reassignment, or once the execution is back on its original provider: when the fallback provider hits its own quota and resets first, the sweep retries it and keeps the origin, so the execution still returns to the original worker (tier and model included) after that provider's reset. The return re-checks in its own transaction that the execution is still `Working` or parked on its own quota refusal: a delivery made by the fallback worker in the meantime (`AwaitingReview`) is left alone, never turned into a rejected delivery.

A fallback never picks a provider that cannot take the work yet, so a campaign does not bounce between accounts (Claude → Codex → Claude, a dispatch and a handoff per refusal). The candidates exclude the execution's stored origin provider (the sweep brings it back, a fallback does not) and every provider whose refusal has not reset: an open `quota_exhausted` escalation, or an announced reset still ahead. The refusal a fallback walks away from is therefore recorded in `provider_quota_generations.reset_at` (reset only: it never bumps the generation a human re-arm acknowledges). That global record cannot tell a refusal that announced nothing (it stores no reset), so each execution also keeps the providers that refused it during its own fallback chain (`task_execution_quota_refusals`, migration 287): the provider a fallback leaves is added with the reset it announced, and a refusal without a reset holds until the execution is back on its origin. Those providers are never candidates, so with Claude (origin), Codex and Gemini allowed, Codex's then Gemini's refusal without a reset ends in an escalation after the second, instead of Gemini → Codex → Gemini forever (a dispatch and a handoff per refusal). The rows are deleted with the stored origin: by a human reassignment, or once the execution is back on its original provider and tier. A refusal that announced a reset excludes its provider only until that reset. [src: file: backend/src/db/orchestration.rs:2917#execution_refused_providers] [src: file: backend/src/db/orchestration.rs:2715#provider_quota_unavailable_at]

The stored origin is spent when the execution is back on its original provider and tier, not when a clock says so: a fallback or a return that lands there deletes it, and the sweep skips (and clears the origin of) an execution that already runs on its original worker, since "handing it back" would cancel the live worker. [src: file: backend/src/db/orchestration.rs:2798#is_worker]

The opt-in is reachable from the launch dialog ("Fall back to another allowed agent when the quota runs out", off by default; campaign creation field `quota_fallback`) and, for a single task, from the `quota_fallback_agents` argument of `task_exec_launch` and of `POST /api/orchestration/provision`: the providers the launch lets the execution fall back to, in preference order. Empty or absent means never. Migration 286 adds the flag off for every existing campaign. [src: file: backend/src/db/orchestration.rs:2940#fallback_executions_past_origin_reset]

Every provider switch is journaled (`worker_reassigned` carries `from_provider`). It is shown where the reviewer decides, in the review-request card posted when the worker delivers (`Provider fallback: the execution moved from X to Y`), and again as a `fallback:` attention point of the accepted-delivery report.
