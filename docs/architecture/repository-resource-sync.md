# Repository resource synchronization

Repository resources are materialized only by an explicit publish operation. That operation writes the selected resource together with the generated index, configuration, router skill, lock file, and the `docs/AGENTS.md` pointer; it checks ownership before replacing existing files. [src: file: backend/src/core/repository_resources.rs:844]

Imports accept only relative paths recorded in `kronn.lock` and reject symlink escapes before reading a definition. [src: file: backend/src/core/repository_resources.rs:475]

Alignment is hash-based. The stored repository and database baselines give each resource one of `repository_only`, `kronn_only`, `up_to_date`, `repository_newer`, `kronn_newer`, `conflict` or `approval_required` — a single state, so a single primary action. A resource that exists on both sides but was never aligned has no baseline: equal content is `up_to_date`, anything else is `conflict` rather than a guess at which side is newer. `approval_required` replaces the sync state for imported workflows, Quick Prompts, Quick APIs and Quick Execs until their current hash is approved; skills and artifacts run nothing and never wait for it. [src: file: backend/src/api/projects/resources.rs:277] [src: file: backend/src/api/projects/resources.rs:217]

The listing says *that* the two sides differ (`status`), never *how*: it carries no diff and no file content. For `repository_newer`, `kronn_newer` and `conflict` (and for `approval_required`, whose sync state is one of those), `GET /api/projects/:id/repository-resources/comparison?kind=&id=` returns a unified diff per file (`file_diffs`, the artifact's `index.html` included; `diff` is the main file's) and, for workflows, Quick APIs and Quick Execs, a field-by-field diff (`field_diff`) that ignores instance-local fields. The Compare sheet calls it when it opens, shows a loading state meanwhile, keeps both "keep a side" buttons off until the differences are on screen, and asks for nothing when the two sides agree or only one exists. The line diff trims the unchanged head and tail before its bounded LCS, so a local edit in a large page stays a real hunk. Nothing is chosen automatically. [src: file: backend/src/api/projects/resources.rs:299] [src: file: backend/src/api/projects/resources.rs:1224] [src: file: frontend/src/components/RepositoryResourceCompare.tsx:46] [src: file: backend/src/core/repository_resources.rs:1340]

Rendering a Kronn-side resource (`render_*`) masks every string it holds, which is the expensive part of a listing, so the masked result is memoized in process under a SHA-256 fingerprint of what it was made from: the unmasked definition, the kind, the slug and the timestamp (`ContentMemo`, bounded to 48 MiB, oldest entries out first). The same content is masked once, however many times the listing and the comparison read it; changed content has a new fingerprint and is masked afresh. The memo is never persisted: a masking rule changes with the binary, hence with the process. The masking itself is unchanged; `core::redact` only skips a pattern whose *gate* fails, a literal that every match of that pattern must contain (`Gate`), so text that cannot hold a secret never reaches the regex. A `Prefilter` runs first, once per list of patterns: it looks for the first three bytes of any gate literal (ASCII case folded) and, when none is there, which is the case for the short names, flags and paths that make up most of a resource, it turns the whole list away in one scan. It is asked again after every rewrite, since a replacement can bring literals of its own. A gate or a prefilter that held back a match would leak, so each is checked against its own regexes, on fixed shapes and by property tests that compare the output with and without them (the audit-artifact pipeline included). No write replaces a side silently: publish refuses to overwrite repository changes without `overwrite_repository_changes`, import refuses to replace a Kronn copy that holds edits the repository lacks without `overwrite_kronn_changes` (the baseline decides, or the repository file when there is none), and copying a native skill refuses to replace an edited Kronn copy the same way. [src: file: backend/src/api/projects/resources.rs:1414] [src: file: backend/src/api/projects/resources.rs:1113]

Each entry states its dates: the repository side is the last commit's author and date when git knows the file, else the file mtime; the Kronn side is the resource's `updated_at` (a custom skill's file mtime); `aligned_at` is the stored baseline. The repository dates are read once per listing (`RepositoryFileDates`: one `git ls-files` and one `git log` that stops as soon as every tracked file is resolved, over the folders that exist, within a 600 ms budget after which the files not yet dated fall back to their mtime), never one `git log` per file — a path absent from the repository has no date and costs no lookup. Both sides carry an eight-character `*_fingerprint` of their content hash, absent for a side without a file. Every entry lists `write_preview`, all the paths a publish would write, including the shared scaffold and `docs/AGENTS.md` while its Kronn line is missing. The listing also reports `can_write_repository` and, when false, `can_write_repository_reason` as a code the UI words in its own language (`kronn_path_is_file`, `repository_read_only`, `repository_unreadable`), never a raw error message, plus `uncommitted_managed_paths` from a single `git status` over the lock's files. `required_secrets` are the names the repository files reference as `secret://NAME`. Each is `configured` when it is a stored env key of an MCP or API config the project can use (its own or a global one): names only, no value is read. Each entry also carries its ADR-005 level, `N2` for workflows and Quick APIs (which declare `requires: [kronn]`). A native skill outside `kronn/` (`.claude/skills`, `.agents/skills`…) is `native_skill` and is grouped by slug across those folders, every origin path kept and `repository_paths_diverge` set when the copies differ. "Use in Kronn" records a read-only path reference in `project_skill_references`, with no `kronn.lock` entry; "Copy into Kronn" creates a catalog skill attached to the project and writes nothing into the repository, replacing an edited copy only when the request says `overwrite_kronn_changes`. Every skill has a defined `status`, never null. A skill only in Kronn's catalog is `kronn_only`; when the repository's stack proposes it (`detect_project_skill_markers`: a `Dockerfile` proposes `devops`), it is also `suggested` with `suggested_reason` naming the detected file, and it is never presented as a repository file or as something to process — the only action is to attach it. A catalog skill found in a native folder without being attached is `repository_only`; an attached one is `kronn_only`, or `repository_newer` once a file already sits at its publication path. The file names Kronn writes for a new resource are plain ASCII (`ascii_slug` folds accents: `réduit` becomes `reduit`); a slug already recorded for an existing resource is never recomputed, so nothing already published is renamed. [src: file: backend/src/core/repository_resources.rs:122]

Alignment baselines and approvals are local SQLite state rather than repository files. Approvals are keyed by project, resource kind, slug, and content hash, so a changed executable definition requires a new approval. [src: file: backend/src/db/sql/200_repository_resource_alignment.sql:4] [src: file: backend/src/db/sql/200_repository_resource_alignment.sql:19]

The executable fingerprint excludes local identifiers, timestamps, favorites, and workflow activation state while retaining the portable definition. [src: file: backend/src/core/repository_resources.rs:108]

Imported workflows, Quick Prompts, Quick APIs, and Quick Execs share the same fingerprint-bound execution check. Standalone launches report approval failures as preflight failures, while workflow references are checked while hydrating the saved resource before any agent or plugin execution.
