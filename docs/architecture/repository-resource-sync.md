# Repository resource synchronization

Repository resources are materialized only by an explicit publish operation. That operation writes the selected resource together with the generated index, configuration, router skill, lock file, and the `docs/AGENTS.md` pointer; it checks ownership before replacing existing files. [src: file: backend/src/core/repository_resources.rs:844]

Imports accept only relative paths recorded in `kronn.lock` and reject symlink escapes before reading a definition. [src: file: backend/src/core/repository_resources.rs:475]

Alignment is hash-based. The stored repository and database baselines give each resource one of `repository_only`, `kronn_only`, `up_to_date`, `repository_newer`, `kronn_newer`, `conflict` or `approval_required` — a single state, so a single primary action. A resource that exists on both sides but was never aligned has no baseline: equal content is `up_to_date`, anything else is `conflict` rather than a guess at which side is newer. `approval_required` replaces the sync state for imported workflows, Quick Prompts, Quick APIs and Quick Execs until their current hash is approved; skills and artifacts run nothing and never wait for it. [src: file: backend/src/api/projects/resources.rs:347] [src: file: backend/src/api/projects/resources.rs:237]

The listing says *that* the two sides differ (`status`), never *how*: it carries no diff and no file content. For `repository_newer`, `kronn_newer` and `conflict` (and for `approval_required`, whose sync state is one of those), `GET /api/projects/:id/repository-resources/comparison?kind=&id=` returns a unified diff per file (`file_diffs`, the artifact's `index.html` included; `diff` is the main file's) and, for workflows, Quick APIs and Quick Execs, a field-by-field diff (`field_diff`) that ignores instance-local fields. The Compare sheet calls it when it opens, shows a loading state meanwhile, keeps both "keep a side" buttons off until the differences are on screen, and asks for nothing when the two sides agree or only one exists. The line diff trims the unchanged head and tail before its bounded LCS, so a local edit in a large page stays a real hunk. Nothing is chosen automatically. [src: file: backend/src/api/projects/resources.rs:302] [src: file: backend/src/api/projects/resources.rs:1281] [src: file: frontend/src/components/RepositoryResourceCompare.tsx:46] [src: file: backend/src/core/repository_resources.rs:1340]

Rendering a Kronn-side resource (`render_*`) masks every string it holds, which is the expensive part of a listing, so the masked result is memoized in process under a SHA-256 fingerprint of what it was made from: the unmasked definition, the kind, the slug and the timestamp (`ContentMemo`, bounded to 48 MiB, oldest entries out first). The same content is masked once, however many times the listing and the comparison read it; changed content has a new fingerprint and is masked afresh. The memo is never persisted: a masking rule changes with the binary, hence with the process. The masking itself is unchanged; `core::redact` only skips a pattern whose *gate* fails, a literal that every match of that pattern must contain (`Gate`), so text that cannot hold a secret never reaches the regex. A `Prefilter` runs first, once per list of patterns: it looks for the first three bytes of any gate literal (ASCII case folded) and, when none is there, which is the case for the short names, flags and paths that make up most of a resource, it turns the whole list away in one scan. It is asked again after every rewrite, since a replacement can bring literals of its own. A gate or a prefilter that held back a match would leak, so each is checked against its own regexes, on fixed shapes and by property tests that compare the output with and without them (the audit-artifact pipeline included). No write replaces a side silently: publish refuses to overwrite repository changes without `overwrite_repository_changes`, import refuses to replace a Kronn copy that holds edits the repository lacks without `overwrite_kronn_changes` (the baseline decides, or the repository file when there is none), and copying a native skill refuses to replace an edited Kronn copy the same way. [src: file: backend/src/api/projects/resources.rs:1414] [src: file: backend/src/api/projects/resources.rs:1113]

Each entry states its dates: the repository side is the last commit's author and date when git knows the file, else the file mtime; the Kronn side is the resource's `updated_at` (a custom skill's file mtime); `aligned_at` is the stored baseline. The repository dates are read once per listing (`RepositoryFileDates`: one `git ls-files` and one `git log` that stops as soon as every tracked file is resolved, over the folders that exist, within a 600 ms budget after which the files not yet dated fall back to their mtime), never one `git log` per file — a path absent from the repository has no date and costs no lookup. Both sides carry an eight-character `*_fingerprint` of their content hash, absent for a side without a file. Every entry lists `write_preview`, all the paths a publish would write, including the shared scaffold and `docs/AGENTS.md` while its Kronn line is missing. The listing also reports `can_write_repository` and, when false, `can_write_repository_reason` as a code the UI words in its own language (`kronn_path_is_file`, `repository_read_only`, `repository_unreadable`), never a raw error message, plus `uncommitted_managed_paths` from a single `git status` over the lock's files. A native skill outside `kronn/` (`.claude/skills`, `.agents/skills`…) is `native_skill` and is grouped by slug across those folders, every origin path kept and `repository_paths_diverge` set when the copies differ. "Use in Kronn" records a read-only path reference in `project_skill_references`, with no `kronn.lock` entry; "Copy into Kronn" creates a catalog skill attached to the project and writes nothing into the repository, replacing an edited copy only when the request says `overwrite_kronn_changes`. Every skill has a defined `status`, never null. A skill only in Kronn's catalog is `kronn_only`; when the repository's stack proposes it (`detect_project_skill_markers`: a `Dockerfile` proposes `devops`), it is also `suggested` with `suggested_reason` naming the detected file, and it is never presented as a repository file or as something to process — the only action is to attach it. A catalog skill found in a native folder without being attached is `repository_only`; an attached one is `kronn_only`, or `repository_newer` once a file already sits at its publication path. The file names Kronn writes for a new resource are plain ASCII (`ascii_slug` folds accents: `réduit` becomes `reduit`); a slug already recorded for an existing resource is never recomputed, so nothing already published is renamed. [src: file: backend/src/core/repository_resources.rs:122]

Alignment baselines and approvals are local SQLite state rather than repository files. Approvals are keyed by project, resource kind, slug, and content hash, so a changed executable definition requires a new approval. [src: file: backend/src/db/sql/200_repository_resource_alignment.sql:4] [src: file: backend/src/db/sql/200_repository_resource_alignment.sql:19]

The executable fingerprint excludes local identifiers, timestamps, favorites, and workflow activation state while retaining the portable definition. [src: file: backend/src/core/repository_resources.rs:108]

Imported workflows, Quick Prompts, Quick APIs, and Quick Execs share the same fingerprint-bound execution check. Standalone launches report approval failures as preflight failures, while workflow references are checked while hydrating the saved resource before any agent or plugin execution. Each entry also lists the resources it points at (`uses`) and those that point at it (`used_by`), as `{ kind, id, slug, name, missing }`. A workflow's steps reference Quick Prompts, Quick APIs, Quick Execs, sub-workflows and Artifacts by id (a dynamic `{{…}}` page id names nothing saved and is skipped); an Artifact's action blocks reference workflows and Quick resources; Quick Prompts, Quick APIs and Quick Execs reference nothing. The edges come from the Kronn definition and from the repository file, whose foreign ids resolve through the `id` recorded in the other files of `kronn.lock`, so a workflow that has not been imported yet still lists what it needs. A reference that no resource of the project answers to is kept with `missing: true`, and a resource never links to itself. The graph reads nothing the listing does not already read: the Kronn-side edges come from the definition each row is rendered from (already masked and memoized), and each repository file is read once more for its own edges. On 120 resources, 40 of them workflows of 15 steps, that is about 2 ms with nothing published and about 9 ms with every repository file present (out of about 100 ms for the whole listing, debug binary; `listing_speed_with_workflows_linking_many_prompts`), and the links lists sit on the Compare sheet from the first paint while its diff is still loading. The panel keeps a selection closed under `uses`: ticking a resource ticks its whole dependency closure (walked once, so a loop terminates), a resource a ticked one still needs cannot be unticked (the reason names the requirer), and two resources that need each other are unticked together. "Align all" applies the same rule to its lines. Skills are real Agent Skills, in `.agents/skills`, never in `kronn/`. Writing a skill into the repository produces `.agents/skills/<slug>/SKILL.md` in the standard format (<https://agentskills.io/specification>): `name` is the folder slug (1-64 lowercase letters, digits and single hyphens), `description` is 1-1024 characters (an empty one falls back to the skill's display name, an oversized one is cut), `license` and `allowed-tools` keep their standard fields, and what is Kronn's own — display name, icon, category, attribution — goes under `metadata` (`kronn-name`, `kronn-icon`, `kronn-category`, `kronn-external`, `kronn-source-url`). The body is the skill's content, with no Kronn blob in it; the rendering is validated before it is written, so an invalid header is never published. `kronn/` keeps only what has no native home: prompts, quick execs, quick APIs, workflows and artifacts. Reading a skill back (`read_resource`, "Use in Kronn", "Copy into Kronn") understands both the standard file and the former `kronn/skills` format. A skill that moves keeps its identity: the lock entry's path, the ownership record of the file (`kronn.lock`'s `files`) and its content hash follow it, while the slug — what `resource_identities`, the alignment baseline and the fingerprint approvals are keyed by — does not change, and the approval hash covers the definition, not the path. Publishing a skill that `kronn.lock` still lists under `kronn/skills/` writes it to `.agents/skills/` and removes the former file when it is still exactly what Kronn wrote (a human edit is refused unless `overwrite_repository_changes`), so the skill never exists twice. A skill still under `kronn/skills/` is listed as never aligned, its repository side compared as the standard file a move would write, so the change of file format alone is never a difference. "Migrate everything to .agents/skills" gathers the skills found in `.claude/skills`, `.gemini/skills`, `.codex/skills`, `.github/skills`, `.opencode/skill(s)`, `.cursor/skills` and `kronn/skills` into `.agents/skills`, in two steps. `GET /api/projects/:id/repository-resources/skills/migration` reads the repository and returns the recap without writing: every move (source → target, flagged when the target already holds the same content, when a `kronn/skills` file is rewritten in the standard format, and when Kronn tracks it in the lock), every conflict (same slug, different contents, with the folders holding each version) and every folder left in place (`symlink`, `unreadable`, `reserved_slug` for `.agents/skills/kronn`, `target_occupied`, `too_large`). `POST .../skills/migrate` recomputes the plan and applies it: a conflict is written only when the request names the folder whose version to keep (`resolutions`), otherwise it is skipped and reported (`unresolved`); a source folder is removed only when the target now holds its exact content (file by file, and a file that changed since it was read stays), so a version that was not chosen is kept where it was (`kept`), never overwritten. The lock, the alignment baseline and the "Use in Kronn" path references follow the moved skills; a baseline that cannot be shown equal to the new file is dropped, which reads as a conflict for a human, never a guess. Nothing is committed: `uncommitted_managed_paths` counts the lock's files, everything under `.agents/skills`, and the deletions under the source folders, so the "not committed" banner shows the work waiting.
