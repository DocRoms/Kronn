# Repository resource synchronization

Repository resources are materialized only by an explicit publish operation. That operation writes the selected resource together with the generated index, configuration, router skill, lock file, and the `docs/AGENTS.md` pointer; it checks ownership before replacing existing files. Imports accept only relative paths recorded in `kronn.lock` and reject symlink escapes before reading a definition. [src: file: backend/src/core/repository_resources.rs:475]

Alignment is hash-based. The stored repository and database baselines give each resource one of `repository_only`, `kronn_only`, `up_to_date`, `repository_newer`, `kronn_newer`, `conflict` or `approval_required` — a single state, so a single primary action. A resource that exists on both sides but was never aligned has no baseline: equal content is `up_to_date`, anything else is `conflict` rather than a guess at which side is newer. `approval_required` replaces the sync state for imported workflows, Quick Prompts, Quick APIs and Quick Execs until their current hash is approved; skills and artifacts run nothing and never wait for it. [src: file: backend/src/api/projects/resources.rs:347] [src: file: backend/src/api/projects/resources.rs:237]

The listing says *that* the two sides differ (`status`), never *how*: it carries no diff and no file content. `GET /api/projects/:id/repository-resources/comparison?kind=&id=` is asked for when a resource's sheet ("View", "Compare") opens, and answers for every resource, whatever its state: `files` lists each file with its text on each side that holds it (`repository` and `kronn`, both masked by the same pass before anything else is done with them; either is absent when that side has no file, and a side is cut at 512 KiB, after masking, and flagged `truncated`), the main file first. The repository's side is masked too because a file in Git can hold a secret someone typed into it by hand, which Kronn's rendering never saw: the texts, the unified diffs and the repository values of `field_diff` all come out of `masked_text` (`core::redact::redact_for_audit_artifact`, memoized by the SHA-256 of the content like the renderings), so one side never shows what the other hides and a secret both sides hold is not a difference. A `secret://NAME` reference, which the masking patterns would take for a value (`password=secret://NAME`), is kept readable on a line where it is all there is to hide, so the sheet still names the secrets a resource needs; a line with anything else to mask, or a "reference" whose name would itself be masked, is masked whole. For `repository_newer`, `kronn_newer` and `conflict` (and for `approval_required`, whose sync state is one of those) it also returns a unified diff per file (`file_diffs`, the artifact's `index.html` included; `diff` is the main file's) and, for workflows, Quick APIs and Quick Execs, a field-by-field diff (`field_diff`) that ignores instance-local fields. Which files each side has follows the listing's own reading of the row: a skill `kronn.lock` lists is aligned against its baseline, an attached one is set against its publication path, one only found in a native folder (`repository:<slug>`, or a catalog skill not attached) is that folder's files with no Kronn side, and a catalog skill alone (built-in or written by the user) is Kronn's rendering, and its row opens the same sheet as any other, with only the Kronn mode on; a repository-only resource (`repository:<kind>:<slug>`) is the lock entry's files. The sheet shows a loading state meanwhile, keeps both "keep a side" buttons off until the differences are on screen, and reads its modes from what came back: *Repository* and *Kronn* are off when that side has no text ("not in the repository", "not in Kronn"), *Diff* is off when only one side exists or the texts are identical. It opens on Repository when only the repository has the resource, on Kronn when only Kronn has it or the two are identical, and on Diff when they differ, adding "the repository is newer" or "Kronn is newer" only for `repository_newer` / `kronn_newer` (a `conflict` moved on both sides and names neither). A skill's `SKILL.md` is shown as Markdown (no raw HTML, only web links followed, images reduced to their caption) or as source; every other file is text. The line diff trims the unchanged head and tail before its bounded LCS, so a local edit in a large page stays a real hunk. Nothing is chosen automatically. Rendering a Kronn-side resource (`render_*`) masks every string it holds, which is the expensive part of a listing, so the masked result is memoized in process under a SHA-256 fingerprint of what it was made from: the unmasked definition, the kind, the slug and the timestamp (`ContentMemo`, bounded to 48 MiB, oldest entries out first). The same content is masked once, however many times the listing and the comparison read it; changed content has a new fingerprint and is masked afresh. The memo is never persisted: a masking rule changes with the binary, hence with the process. The masking itself is unchanged; `core::redact` only skips a pattern whose *gate* fails, a literal that every match of that pattern must contain (`Gate`), so text that cannot hold a secret never reaches the regex. A `Prefilter` runs first, once per list of patterns: it looks for the first three bytes of any gate literal (ASCII case folded) and, when none is there, which is the case for the short names, flags and paths that make up most of a resource, it turns the whole list away in one scan. It is asked again after every rewrite, since a replacement can bring literals of its own. A gate or a prefilter that held back a match would leak, so each is checked against its own regexes, on fixed shapes and by property tests that compare the output with and without them (the audit-artifact pipeline included). The memo is filled ahead of the first request, and read without copying (KT-915). A background task (`Prewarm`, spawned by both binaries, `backend/src/main.rs` and `desktop/src-tauri/src/main.rs`) renders the workflows, Quick Prompts, Quick APIs, Quick Execs and Artifacts of every project into that same memo, under the slugs and from the content the listing uses, two seconds after the backend starts and again once the resources of the database have been quiet for 1.5 s after an edit (never later than 15 s after the first edit of a burst, so a workflow filling a dataset cannot keep it waiting). It is a low-priority guest: it reads the database in short slices (one project's automations, then one Artifact at a time) so the read connection is free between them, masks in `spawn_blocking` outside any database lock, breathes 2 ms between two resources, stops between two resources at shutdown, and stops for the run when the memo is seven eighths full instead of evicting what it just computed — it never takes more memory than the memo's own 48 MiB. Skills are not warmed: their rendering is pinned to a date that comes from each project's alignment records. The edits are heard from SQLite itself: an update hook on the write connection raises a signal for any row written to the tables a rendering is made of (`db::resource_changes`), so a resource written by the API, an agent tool, an import or a workflow run all count, and changes raised while a run is going are kept as one. A rendering is a cheap value: its document and files are shared with the memo (`Arc`), so serving a resource from memory copies a few short strings rather than the JSON tree and the file bytes, and the listing reads each resource once (`LoadedResource`, only the project's own rows) and each repository file once. Two constraints shaped this. The memo key is built from the resource *as a JSON `Value`*, whose object keys are sorted, never from the typed struct: `Workflow` and `Quick API` hold `HashMap`s, which serialize in a different order each time they are loaded, and a key that moved with them would never be found again. And the approval fingerprint (`approval_hash`) keeps its exact bytes — a human's approval is stored against it — which a golden test pins for every kind, next to golden tests of the rendered files and of the listing. A skill can declare variables (KT-906). The names use the Claude Code `arguments` field, a YAML list or a space-separated string mapped to positions in order, substituted as `$name` in the body, with an optional `argument-hint` (<https://code.claude.com/docs/en/skills.md>); the Agent Skills specification has no such field, so other agents read `$name` as written. A name must start with an ASCII letter or `_` and hold only letters, digits, `_` and `-` (a leading digit would read as the positional `$0`). Kronn's own description of each variable (label, description, required, default, control) is a JSON list under the flat `metadata.kronn-variables` key, because `metadata` is a string map and Kronn has no YAML crate; each entry must name a declared argument, once. Kronn writes `arguments` as a JSON array (valid YAML flow), reads all three Claude shapes, and a malformed variable list is a validation error on publication but never hides a skill that is only read: the skill loads with its arguments and no variables. `Skill.arguments`, `argument_hint` and `variables` expose them, and a skill with arguments carries the "Variabilisé" badge in every skill list.
