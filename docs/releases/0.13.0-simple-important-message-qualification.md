## What the human-facing change proves

- **Plain authoring, separate from the plan.** The form offers Information,
  Decision and Blocker, plain text and an optional existing task. The key field
  exists only inside the open form. Ordinary composer content and sending stay
  independent; publication does not create, complete or edit a task.
- **Real task navigation.** Options come from the active room's actual plan.
  The card resolves a fresh plan and opens that task, not the previously selected
  task. Missing tasks and failed reads have explicit errors. Component tests
  include disabled browser storage; real browser tests compare the complete
  task before and after publication/navigation for equality.
- **Bounded lifecycle.** Drafts are separate per room in memory and survive
  closing the form, room changes and visiting Settings, not a browser reload.
  Preparation cancellation cannot issue a late write. A started write remains
  observed, and only a matching persisted card confirms publication. An
  uncertain retry freezes the original body and UUID, including when its old
  task link has subsequently disappeared. A confirmed text-only attempt needs
  a new explicit publication UUID; an ordinary row is never promoted in place.
- **Existing authority retained.** The form uses the same enrolled credential
  and single-use proof. Authority material never enters the draft/outbox,
  message, URL or browser storage. Backend tests keep worker refusal, identity
  checks, room/content binding and replay behavior. These are API controls, not
  protection from an actor already able to read another process's OS secrets.
- **Actual mobile and desktop paths.** The 360px and 1280px cases use the real
  application/backend, check viewport containment and reachable publishing,
  issue two synchronous button clicks and require exactly one message POST,
  then follow the persisted Information card to its unchanged plan task.
