# 0.14.1 — fluidity audit on real data (KT-720)

What a user feels on Automations, Plugins and Discussions, measured in a real
browser on the maintainer's own instance, with the causes found and what the
0.14.1 fixes changed.

## Environment and volumes

- Native development stack (`kronn start-dev`): Vite dev server, Rust backend
  on the host. Development builds are slower than a production bundle; where a
  production figure exists it is quoted separately.
- Real data, not a fixture: 776 discussions, 39 workflows, 23 plugin servers,
  23 Quick Prompts, 49 Quick APIs, a database of about 7 GB. The heaviest room
  (`85513703`) holds 2,173 messages, a 3.2 MB detail and 14 attachments
  (12 images, 2 clips).
- Background activity was not stopped: other rooms, a running workflow and
  agent builds were live during several runs. Figures below are single runs
  unless stated, so treat them as orders of magnitude, not benchmarks.

## Protocol

`node scripts/perf/ui-fluidity-journey.mjs --room <id>` replays one journey:
boot, then Automations, Plugins and Discussions twice (cold, then warm) with a
scroll, a search and 10 s at rest on each, then opens the heavy room and stays
20 s. Per step it records Event Timing (input to next paint), long tasks, DOM
size, and the API requests with their size. It answers every non-GET API call
with a local 503, so it never writes to the instance, and it traces the JS
caller of every full discussion-detail fetch and counts WebSocket frames by
type, which is how the reload causes below were attributed.

## Results

| Surface | Measured | Verdict |
|---|---|---|
| Automations | navigation under 70 ms; scroll 0.6–0.75 s with one long task of ~110–155 ms; at rest, one ~135–175 ms long task at each 10 s `/api/workflows` refresh | fine; the refresh task is the only visible cost |
| Plugins | navigation under 120 ms (up to ~190 ms warm); search keystroke 24–48 ms; nothing at rest | fine |
| Discussions list | 1–2 s, 4 long tasks (max 180 ms), ~0.9 MB | acceptable |
| Heavy room, opening | before: 11–31 s, 17–20 long tasks, 30–66 MB; after: 5.9 s, 12 long tasks, 17 MB | fixed in part (KT-776, KT-777), rest is KT-733 |
| Heavy room, 20 s at rest | before: 1.9 MB, and up to 27 MB while a workflow ran; after: 1.9 MB with a workflow running, no full-detail fetch | fixed (KT-734, KT-753, KT-776) |

## Causes found and fixes

- **Automations — latest run of each workflow (KT-732).** The listing scanned
  every run row, including gigabytes of step results. A
  `(workflow_id, started_at)` index answers it: 0.85–3.7 s → 19 ms on the
  real database. Measured on the backend query, not in the browser.
- **Open discussion — full transcript every 5 s (KT-734).** The refresh now
  sends the revision it holds and the server omits an unchanged detail:
  3.3 MB → about 90 bytes per refresh at rest.
- **Live Pages — detail fetched twice per cycle (KT-736).** One fetch per
  refresh.
- **Large room freezing at rest (KT-753).** Unrelated refreshes re-rendered all
  2,000 bubbles. Production build: long tasks per 20 s at rest from a median of
  925 ms to about 370 ms.
- **Reloads triggered by unrelated events (KT-776).** Every
  `shared_run_updated` — from any workflow or media run — and every reconnect
  reloaded the open discussion through the full detail GET, several at once
  (six 3.2 MB fetches in the same millisecond were traced). The 5 s refresh
  also lost its known revision each time its effect re-ran. Reloads now share
  one revision per discussion and collapse into one poll in flight plus one
  trailing poll. Opening the heavy room during a workflow: 66 MB → 27 MB;
  20 s at rest: up to 27 MB → 1.9 MB.
- **Every image downloaded at opening (KT-777).** Each thumbnail is the whole
  file, and all of them loaded at mount. They now load as they near the
  screen: 15.6 MB → 9.5 MB at opening in the heavy room, every image still
  showing once scrolled to.

## What remains

- **The transcript still mounts every bubble (KT-733, deferred).** About
  175,000 DOM nodes and 5–10 s of cumulated long tasks at opening in a
  development build. Only virtualisation removes that cost.
- **The poll is cheap on the wire, not on the server.** The backend still
  builds and hashes the full detail on every refresh to compare revisions.
- **Automations refresh.** One long task of ~150 ms every 10 s while the page
  is open; noticeable only when interacting at that moment.

## Limits

- Development builds, one machine, with live background activity. There was no
  browser measurement of Automations before KT-732, so its effect is quoted from
  the backend query alone.
- Playwright's `scrollIntoViewIfNeeded` does not reach the oldest attachment
  inside the transcript's scroll container. Thumbnail loading was confirmed with
  wheel scrolling instead.
