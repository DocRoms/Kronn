# 0.13.0 — application icons regenerated from the canonical SVGs

The shipped application icons were not derived from the mark they were meant to
show. At 512 px the difference is plain: the mark renders as a crisp vector,
the shipped icon carried a soft halo and a gradient ground the source does not
produce. At 32 px the two are close enough that the drift went unnoticed.

`site/apple-touch-icon.png` was already corrected separately; this pass covers
the application assets.

## Two sources, on purpose

The desktop and web icons do **not** share a source, and that is deliberate —
each SVG says so in its own comment:

| Source | viewBox | Ground |
|---|---|---|
| `desktop/src-tauri/icons/icon.svg` | `0 0 512 512` | dark plate `#0b0f22` |
| `frontend/public/favicon.svg` = `site/favicon.svg` | `38 48 436 436` | transparent |

A desktop icon lands on a dock or a wallpaper and needs its own ground; a
favicon lands on browser chrome that already is one. Rendering the desktop
icons from the favicon would have silently dropped the plate. Each family was
therefore rendered from its own source, and the check enforces that pairing.

This is asserted on measured pixels, not on the comments: the desktop source
opens with a full-bleed `<rect width="512" height="512" fill="#0b0f22"/>` and
its 512 px render is opaque across all 262 144 pixels, while the web source has
no ground primitive at all and leaves 22 416 of 32 400 pixels fully clear at
180 px. The check fails if either expectation stops holding.

The two web sources are byte-identical, and the check fails if they diverge.

## Method

Chromium via the frontend's Playwright, headless, `deviceScaleFactor: 1`, the
SVG passed as a base64 `data:` URI so no request leaves the page, every capture
taken twice and compared byte for byte, and every route aborted with an
assertion that zero requests occurred. The sources are re-read after the run
and compared to prove they were not modified. Playwright is located in this
checkout or, from a worktree, in the main checkout found through Git metadata —
no path is hard-coded.

This is the method used for `site/apple-touch-icon.png`, reused rather than
reinvented. The cross-check below shows it reproduces that result exactly.

## What changed

Sixteen PNG files and two containers — eighteen assets:

- tauri bundle entries — `32x32`, `64x64`, `128x128`, `128x128@2x` (256), `icon.png` (512)
- Windows Store logos — `Square30x30`, `Square44x44`, `StoreLogo` (50), `Square71x71`,
  `Square89x89`, `Square107x107`, `Square142x142`, `Square150x150`, `Square284x284`,
  `Square310x310`
- `frontend/public/apple-touch-icon.png`
- `icon.ico` — 16, 24, 32, 48, 64, 256, all PNG payloads, same size set as before
- `icon.icns` — rebuilt through `iconutil --convert icns` from a standard iconset

`site/apple-touch-icon.png` was already correct and is unchanged. The check
covers seventeen PNGs: these sixteen plus that unchanged one.

## Evidence

**Cross-check against the previous task.** Rendering `frontend/public/favicon.svg`
at 180 px produced sha256 `9dc493055d76325f…`, byte-identical to the
`site/apple-touch-icon.png` regenerated earlier from the same drawing by a
different agent. Same source, same method, same bytes — which is what makes the
frontend copy's previous divergence a real finding rather than a judgement call.

**Reproducible check.** `node scripts/check-app-icons.mjs --verbose` re-renders
all seventeen PNGs and compares them byte for byte with the shipped files, then
parses both containers and every reference that points at them. It exits 0
today. It fails when an icon is hand-edited, resampled, or regenerated by
another tool — not only when it looks wrong.

Containers are checked structurally and on content. The ICO must declare
`reserved = 0`, type 1, a non-zero count, unique exact `width`×`height` entries
whose offsets and lengths stay inside the file, and PNG payloads whose IHDR
dimensions match what the directory claims. The ICNS header length must equal
the file length, and block traversal must tile the file exactly — a malformed
length fails instead of ending the walk early, which is what a lenient parser
would have reported as success. All eight retained PNG types are required at
their exact pixel size.

Content is compared on decoded pixels, not bytes: the packaging tools write
their own encodings, so each of the fourteen embedded images (six in the ICO,
eight in the ICNS, up to 1024 px) is decoded and compared RGBA against a fresh
render of the desktop source at that size. All fourteen match exactly today.

**Negative tests.** `node scripts/check-app-icons.test.mjs` rebuilds containers
in memory from payloads parsed out of the shipped assets — nothing on disk is
mutated — and asserts that each fault is rejected: truncated files, inflated and
impossible block lengths, out-of-bounds and zero-length entries, a duplicated
required entry, a missing one, a non-PNG payload, and a substituted image whose
real dimensions contradict what its entry declares. It needs no browser and no
network.

**When Playwright is absent** the run prints `NOT VALIDATED`, names the
directories it searched, and exits 2. That is a non-success: no icon was
checked, and it must not be read as a pass.

## Declared differences and limits

**The ICNS container changed shape.** `iconutil` emits today's formats, so four
entries are gone — `is32`, `il32`, `s8mk`, `l8mk`, 16 and 32 px bitmaps with
separate 8-bit masks — and three appear: `ic04`, `ic05` and `info`. All eight
PNG entries are retained and verified at their exact size: `ic11` (32), `ic12`
(64), `ic07` (128), `ic13` and `ic08` (256), `ic14` and `ic09` (512), `ic10`
(1024). The file goes from 1 557 009 to 438 761 bytes.

The limit is stated rather than argued: **which entry a given macOS version
selects was not tested.** No system was observed choosing one, and the removed
entries' absence was not exercised on a real machine. What is established is
what the container now holds, and that each retained entry carries the current
drawing.

**Not verified here:** no application was packaged, installed or launched, so
this does not prove how the icons look in a dock, a taskbar or a Store listing.
No Rust or Tauri build was run. The visual comparison was made on rendered PNGs
at 512 and 32 px, not on platform-composited output.

**Re-encoded PNGs fail the check even when they look right.** A later commit
re-encoded the fifteen desktop PNGs without changing a pixel, and the byte
comparison failed on all of them. The tool that did it was not identified. If
the check fails again with pixel-identical files, restore the bytes from the
commit that last passed (`git checkout <commit> -- desktop/src-tauri/icons/*.png`)
rather than relaxing the check: byte identity is what catches a resample.

**Unchanged on purpose:** both source SVGs, the drawing itself, every reference
in `tauri.conf.json`, `frontend/index.html` and the three site pages, and
`site/apple-touch-icon.png`.

**References checked:** the five `bundle.icon` entries and, separately, the tray
icon at `app.trayIcon.iconPath` — `icons/icon.png`, which sits outside the
bundle list and is therefore easy to miss. The check requires that it exists and
that it is one of the files regenerated here.
