- **ID**: TD-20260721-edit-resend-presence-dispatch
- **Area**: Backend / Frontend / Discussions / MCP presence
- **Problem (fact)**: Superseded in the code by the atomic revise path. As reported on 2026-07-21, “Edit and resend” chained a DELETE of the trailing replies, a PATCH of the last User row and an unguarded `/api/discussions/{id}/run`; it no longer does. `handleEditMessage` makes one `reviseMessageStream` call with a per-intent idempotency key [src: file: frontend/src/pages/DiscussionsPage.tsx:3661-3742#handleEditMessage], behind an in-flight ref that rejects a rapid duplicate submit [src: file: frontend/src/pages/DiscussionsPage.tsx:771-779#editingMsgInFlightRef], and that call posts to `/api/discussions/{id}/messages/revise` [src: file: frontend/src/lib/api.ts:2535-2557#reviseMessageStream]. The endpoint resolves each target through `route_human_turn`, which decides ownership by target identity rather than transient presence, so a peer-only target creates no local dispatch [src: file: backend/src/api/discussions/routing.rs:20-40#route_human_turn] [src: file: backend/src/api/discussions/messaging.rs:949-1122#revise_message]. One transaction replaces the User content under a revision CAS, enqueues the local dispatch or none, and records a `message_revision_events` row [src: file: backend/src/db/discussions.rs:3532-3795#revise_message_with_dispatch]. The legacy `PATCH`/`DELETE /messages/last` routes were removed by KT-1598; `/run` remains and force-enqueues a dispatch for the latest User message [src: file: backend/src/api/discussions/messaging.rs:1170-1230#run_agent].
- **Why we can't fix now (constraint)**: No remaining constraint on the revise path: the revision event takes its order from the discussion's `next_message_seq` counter, so deleting trailing rows cannot lower it or reuse an order a peer cursor already covers [src: file: backend/src/db/discussions.rs:3616-3625#event_sort_order], and the trailing Agent/System rows are copied to `message_tombstones` before they leave the live projection [src: file: backend/src/db/discussions.rs:3613-3636#message_tombstones]. The legacy surface (the retry button's `deleteLastAgentMessages` and the in-place `edit_last_user_message`) was closed by KT-1598.
- **Impact**: Editing a shared-room turn can spawn an unexpected paid/local agent, create duplicate responders, interrupt an existing orchestration session, and still fail to notify a persistent peer of the revised content. Reused ordering values can also make later replacement messages invisible to cursor-based waits.
- **Where (pointers)**: `frontend/src/pages/DiscussionsPage.tsx`, `frontend/src/lib/api.ts`, `backend/src/api/discussions/messaging.rs`, `backend/src/api/discussions/crud.rs`, `backend/src/db/discussions.rs`, `backend/src/api/federation.rs`, and the discussion-schema migrations.
- **Suggested direction (non-binding)**: Add a monotonic per-discussion event high-watermark column (for example `discussions.last_allocated_sort_order`), backfilled above the current maximum and incremented transactionally with `UPDATE ... RETURNING`; deletion must never reduce it. Every allocation path, including idempotent MCP bulk import, must use the same allocator. Replace the frontend's DELETE/PATCH/unguarded-run sequence with one atomic edit/resend endpoint that publishes a typed revision event with a fresh order, federates it when shared, and uses the presence lease/obligation CAS to choose exactly one responder owner: connected MCP peer or local runner. Specify the revision event's bridge representation and UI rendering (visible edited marker or intentionally hidden event); it must not masquerade as a new User message. Keep `/run` only as an explicit force-retry escape hatch, but require it to acquire a `runner_owned` obligation instead of bypassing dispatch ownership. Define whether revision history is retained or tombstoned before choosing between a new row and an in-place row update.
- **Acceptance criteria**: With one or more active MCP peers, an edited turn appears once as a typed revision beyond every peer's prior cursor and no local CLI starts; without a live peer, exactly one local runner starts; rapid double submit remains idempotent; deleting trailing replies never reuses a prior event order; a cursor greater than the maximum order of the surviving message rows is explicitly valid after deletion; MCP bulk import cannot bypass the shared allocator; a federated mirror receives the same revision semantics; explicit force retry starts exactly one local agent through a `runner_owned` obligation; tests cover concurrent edit/resend and the cursor high-watermark across deletion.
- **Next step**: write the schema/API contract and concurrency tests together with the pending discussion-presence lease/obligation work before implementing the UI switch.
- **Status**: RESOLVED (KT-1598) — the retry button now calls `reviseMessageStream` (same turn content and targets, fresh idempotency key, tombstones and a revision event); `PATCH`/`DELETE /messages/last`, their handlers, DB functions and `api.ts` helpers are removed. `/run` stays as the explicit force-retry escape hatch. Tests: `retry_through_revise_with_a_live_mcp_peer_starts_no_local_cli`, `forced_run_takes_a_durable_runner_obligation`, `forced_run_on_a_peer_owned_turn_starts_no_local_cli` in `backend/src/api/discussions/messaging.rs`. Retry no longer dead-ends: it sends `drop_departed_targets`, so a target that left the room is dropped and the default responder answers (the receipt's `dropped_targets` drives an info toast; `retry_drops_a_departed_target_and_falls_back_to_the_default_responder`), and a 409 while a reply is running shows “a reply is already running” (`retry_while_a_dispatch_is_active_is_a_409_naming_the_running_reply`; `handleRetry` tests in `frontend/src/pages/__tests__/DiscussionsPage.test.tsx`).
- **About `runner_owned`**: the DoD and the acceptance criteria above name a `runner_owned` obligation, but no such symbol exists in the code and none was added. The role is played by the durable dispatch job (`agent_dispatch_jobs`): a pending row bound to the trigger User message, which is the obligation a local runner owns. `/run` takes it through `enqueue_dispatches_for_trigger`, which enqueues a `force:`-keyed job for the latest User turn and refuses to enqueue when `find_active_for_discussion` already finds an active job [src: file: backend/src/api/discussions/messaging.rs:115-158#enqueue_dispatches_for_trigger] [src: file: backend/src/api/discussions/messaging.rs:1170-1230#run_agent]. The revise path creates the same job in the same transaction as the revision event, or none when a joined peer owns the turn, and rejects with `DispatchInProgress` while one is active [src: file: backend/src/db/discussions.rs:3534-3536#revise_message_with_dispatch]. “Takes a `runner_owned` obligation” therefore means “has a durable dispatch job”; do not search for the identifier.
