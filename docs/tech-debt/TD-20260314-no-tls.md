# TD-20260314-no-tls

- **ID**: TD-20260314-no-tls
- **Area**: Infra (Docker gateway, desktop/native server)
- **Problem (fact)**: Kronn itself still serves plain HTTP: the Docker gateway
  listens on port 80 only, with no TLS server block, and the backend has no
  in-process TLS. `[src: file: .docker/nginx.conf:10-13#listen]`
- **Reduced by KT-1596 (0.15.x)**: exposure beyond loopback is no longer
  possible in clear. The Settings toggle refuses to expose Kronn unless a
  TLS-terminating proxy on the machine is declared (with its public https
  origin); a stale config, or an env-only request, starts on loopback with a
  banner instead of serving the token; Docker refuses to start when published on
  the network without the declaration, or with it while the plain port is still
  published. Behind a declared proxy invites advertise `https`/`wss`, the plain
  backend stays on loopback, the loopback auth bypass is withdrawn, and the
  declaration is owner-only. See `docs/operations/auth-and-tls.md`.
- **Residual (why this stays open)**: in-process TLS — rustls, a generated
  certificate, its fingerprint carried in the P2P invite — is not built: `rcgen`
  and `axum-server` are not in the offline cargo cache. Until it ships, a user
  who wants peers on the network must run a proxy (nginx, Caddy,
  `tailscale serve`); Kronn cannot verify that one is really there.
- **Why we can't fix now (constraint)**: certificates for a local-first app
  (self-signed trust, renewal, desktop bundles) need a plan of their own, and the
  two crates above have to be vendored first.
- **Impact**: security / ease of use when the backend is exposed beyond loopback.
- **Where (pointers)**: `backend/src/core/net_expose.rs` (`boot_bind`,
  `plain_http_exposure_refusal`; the `tls_enabled` input is always `false`),
  `.docker/nginx.conf`, `server.auth_strict_localhost`
  (a Bearer token even on loopback). `[src: file: backend/src/models/setup.rs:223-234#auth_strict_localhost]`
- **Suggested direction (non-binding)**: vendor the TLS crates, serve rustls with
  a generated certificate and carry its fingerprint in the invite, then flip the
  default of `auth_strict_localhost`, as described in
  `docs/operations/auth-and-tls.md`.
- **Next step**: create ticket for in-process TLS.
